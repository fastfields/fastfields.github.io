fastfields.auto

fastfields.auto: a backend-dispatching interface over fastfields wrappers.

Every function here dispatches on the type of the first array argument and forwards the call to the matching backend package:

  • numpy.ndarray -> :mod:fastfields.numpy
  • torch.Tensor -> :mod:fastfields.torch
  • cupy.ndarray -> :mod:fastfields.cupy

Backends are imported lazily: only the backend for the array type actually passed is imported, so fastfields.auto works with any subset of the optional backends installed (only fastfields-helpers -- the pure-Python enums/normalisers, no compiled extension -- is a hard dependency; fastfields.auto never touches the compiled fastfields-dlpack bindings directly). A clear error is raised for an unknown array type, and a clear ImportError if the required backend package (or its own dependency, e.g. torch/cupy) is missing.

Every backend wrapper package exposes the same canonical dt_* / sym_* names, and this module exposes one unified name per operation that maps to each backend's function. Arguments are forwarded unchanged, so each dispatched call shares the signature of the selected backend's function.

This namespace requires no particular compute backend -- it runs against whatever is installed, and :func:dlpack_backend reports which lane that is ("cpu", "cu126", ...). That is the whole of its backend handling, by contrast with :mod:fastfields.cupy, which refuses to import on a CPU-only build, and :mod:fastfields.torch, which refuses a CUDA tensor on one.

The dispatchers are split by category into :mod:._dt (distance transforms), :mod:._sym (compact-symmetric ops), :mod:._resample (resampling / spline coefficients), :mod:._pushpull (spline gather/scatter) and :mod:._reg (spatial regularisers), all built on the shared machinery in :mod:._util.

What is not dispatched here, and why

This module is a dispatcher: it picks a backend from the type of the first array argument and forwards every argument unchanged. Two kinds of operation cannot be reached through it, and both are deliberate.

Builders that take a shape, not an array. field_diag, flow_diag, field_kernel and flow_kernel allocate their output from a rank and a set of penalty weights -- there is no array to dispatch on, so there is nothing for this module to decide. Call them on a concrete backend (fastfields.numpy.field_diag(...)) and pass the result into the dispatched operators. Their *_add/*_sub accumulate forms do take an array and are dispatched.

Adjoints that exist for autograd. pull_backward, push_backward, count_backward and grad_backward are the gradients of the pushpull operators; only :mod:fastfields.torch has an autograd engine, and there they are wired into the forward op's autograd.Function rather than exported. There is nothing uniform to dispatch, so the supported spelling is fastfields.auto.pull(...) followed by .backward() on a torch tensor, or fastfields.dlpack.pull_backward(...) raw.

Operations that some backends have are dispatched with a partial table and raise NotImplementedError naming the backends that do have them -- field_cg (CPU-only in the C++ library, so numpy), field_precond_ / flow_precond_ (numpy and cupy), sym_matvec_backward (numpy and cupy). Listing them with a clear failure is better than omitting them, which would make the asymmetry invisible from here.

If a backend turns out not to have an operation this module says it does -- a mixed install, where fastfields.auto is newer than the wrapper -- the call raises NotImplementedError saying which package to upgrade, not a bare AttributeError from a module the caller never named.

dlpack_backend 

dlpack_backend() -> 'str | None'

Report the compute backend of the installed compiled bindings.

fastfields.auto works against whichever backend is installed and never requires a particular one, so -- unlike :mod:fastfields.cupy (which refuses to import on a CPU-only build) and :mod:fastfields.torch (which refuses a CUDA tensor on one) -- it only reports. This is the one place to ask "which lane did I end up on?" without knowing which wrapper to interrogate.

It is a function rather than a module attribute mirroring fastfields.dlpack.backend on purpose: fastfields.auto must not import the compiled bindings at import time (it dispatches lazily and is usable with no array backend at all), and a module attribute would have to be computed at import.

Returns:

Type Description
str or None

"cpu", "cu126", ... for a labelled build of fastfields-dlpack; None if the installed build carries no label (an unversioned source checkout) or if fastfields.dlpack cannot be imported at all.
