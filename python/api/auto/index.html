fastfields.auto

fastfields.auto adds dispatch, not new operations. Each function in the tables below forwards to the function of the same name in the backend that matches the type of its first array argument, and has that function's signature, so an operation is documented on the page of its backend. The overview explains how the dispatch works.

A backend is listed for an operation when it implements it. Calling an operation on an array whose backend is not listed raises NotImplementedError naming the backends that are.

The module

The module itself, with dlpack_backend and the re-exported enums:

fastfields.auto

Backend-dispatching interface to the fastfields operators.

Every function here looks at the type of its first array argument and forwards the call, unchanged, to the function of the same name in the matching backend:

  • numpy.ndarray: fastfields.numpy
  • torch.Tensor: fastfields.torch
  • cupy.ndarray: fastfields.cupy

Arguments and results pass through untouched, so a dispatched call has the signature of the backend function it selects. The reference page for each operation is the one of its backend; this page documents what is specific to dispatching.

Backends are imported lazily, and only when an array of their type is passed. The package therefore works with any subset of them installed. Its only hard dependency is fastfields.helpers; apart from dlpack_backend, which imports the compiled fastfields-dlpack bindings when it is called, it does not touch them. An object of any other type raises TypeError, and a backend whose package is missing raises ImportError naming what to install.

This namespace does not need any particular compute backend. dlpack_backend reports which one is installed ("cpu", "cu126" and so on). By contrast, fastfields.cupy refuses to import on a CPU-only build and fastfields.torch refuses a CUDA tensor on one.

What is not dispatched here, and why

Two kinds of operation cannot be reached through this module, and both are deliberate.

Builders that take a shape, not an array. field_diag, flow_diag, field_kernel and flow_kernel allocate their output from a rank and a set of penalty weights, so there is no array to dispatch on. Call them on a concrete backend, for example fastfields.numpy.field_diag(...), and pass the result to the dispatched operators. The *_add* and *_sub* accumulate forms take an array and are dispatched.

Adjoints that exist for autograd. pull_backward, push_backward, count_backward and grad_backward are the gradients of the sampling operators. Only PyTorch has an autograd engine, and there they are wired into the forward operation instead of being exported. The supported spelling is fastfields.auto.pull(...) followed by .backward() on a torch tensor, or fastfields.dlpack.pull_backward(...) for the raw function.

Some operations exist on only some backends. They are dispatched with a partial table, and calling one on another backend raises NotImplementedError naming the backends that have it: field_cg (numpy only, because it is CPU-only in the C++ library), field_precond_ and flow_precond_ (numpy and cupy) and sym_matvec_backward (numpy and cupy). Listing them with a clear failure keeps the asymmetry visible.

If a backend lacks an operation that this module says it has, which points to a stale or partial installation, the call raises NotImplementedError saying so, not a bare AttributeError from a module the caller never named.

Bound

Bases: IntEnum

Boundary condition, applied to every spatial axis.

Member Value Beyond the last voxel, the signal
Zero 0 is zero
Replicate 1 repeats the last voxel (coordinates are clipped)
DCT1 2 is symmetric about the centre of the last voxel
DCT2 3 is symmetric about the edge of the last voxel
DST1 4 is antisymmetric about the centre of the last voxel
DST2 5 is antisymmetric about the edge of the last voxel
DFT 6 wraps around (circular)
NoCheck 7 is not handled: coordinates are assumed inbound

DCT2 is the Neumann condition and DST2 the Dirichlet one.

The wrappers take it as the bound argument, as an integer, as a member of this enum or as a name such as "dct2"; see as_bound.

Spline

Bases: IntEnum

Order of the spline used for interpolation.

The members are the integers 0 to 7, from Nearest (0), Linear (1), Quadratic (2) and Cubic (3) up to FourthOrder, FifthOrder, SixthOrder and SeventhOrder (4 to 7).

The wrappers take it as the order argument, as an integer, as a member of this enum or as a name such as "cubic"; see as_spline. The raw fastfields.dlpack bindings and the C++ library call the same argument spline.

dlpack_backend 

dlpack_backend() -> 'str | None'

Report the compute backend of the installed fastfields-dlpack.

This namespace works with whatever backend is installed and never insists on a particular one; this is the place to ask which one that is, without knowing which wrapper to interrogate. It is a function and not a module attribute so that importing fastfields.auto does not have to import the compiled bindings.

Returns:

Type Description
str or None

"cpu", "cu126" and so on for a labelled build. None if the build carries no label (an unversioned source checkout), or if fastfields.dlpack cannot be imported at all.
